# 今日核心知识点

## 1. 接口测试的最小矩阵

测试一个 HTTP 接口，不要只测「正常能跑」，要覆盖至少 4 类场景：

| 场景 | 关注点 | 示例 |
|------|--------|------|
| 正常路径 | 返回正确状态码和数据 | `GET /podcasts` 返回列表 |
| 参数错误 | 返回 400，提示清晰 | `POST /podcasts` 缺少 title |
| 资源不存在 | 返回 404，不抛异常 | `GET /podcasts/999` |
| 服务端异常 | 被错误处理中间件捕获，返回 500 | handler 主动抛错 |

为什么强调可重复运行？因为本地内存数据会被修改（增删改），如果测试脚本不能重置状态，第二次运行就可能失败。今天的 `test.sh` 通过「启动独立进程 + 测试结束后关闭」来保证可重复性。

## 2. demo 工程化的意义

| 阶段 | 特征 | 问题 |
|------|------|------|
| 一个文件跑通 | 快速验证想法 | 别人/一周后自己不知道依赖和运行方式 |
| 可复现工程 | 有 `package.json`、脚本、说明 | 拿到就能跑，便于复盘和面试展示 |
| 可交付项目 | 有测试、CI、文档 | 能进简历 |

今天我们要把本周 demo 从「一个文件跑通」推进到「可复现工程」。

## 3. 文档写什么、不写什么

一份好的 demo README 应该包含：
- 运行环境要求（Node.js 版本、包管理器）
- 安装命令
- 启动命令
- 接口清单与示例 curl
- 项目结构说明

不要写：大段框架原理科普（那是 `knowledge.md` 的事）、与运行无关的个人笔记。

## 4. 测试脚本的工程细节

- 后台启动服务：`node ... &` 后记录 `$!`，`trap` 退出时 `kill $!`。
- 等待服务就绪：`curl --retry` 或 `sleep` 后请求 `/health`。
- 断言：不要只用眼睛看，用 `grep` 或 `jq` 判断返回 JSON 中是否包含预期字段。
